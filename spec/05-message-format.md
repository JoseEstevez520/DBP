# 5. Message Format

This document specifies the wire format for DBP messages, the JSON schema, label encoding, transport mappings, and error handling.

## 5.1 DBPMessage

All data exchanged between agents under DBP is encapsulated in a **DBPMessage**. This is the universal envelope that carries the label, payload, and metadata.

### 5.1.1 JSON Schema

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "DBPMessage",
  "type": "object",
  "properties": {
    "protocol": {
      "type": "string",
      "enum": ["dbp/1.0"],
      "description": "Protocol version identifier"
    },
    "id": {
      "type": "string",
      "format": "uuid",
      "description": "Unique message identifier (UUID v4)"
    },
    "origin": {
      "type": "string",
      "description": "Agent name or identity of the sender"
    },
    "destination": {
      "type": "string",
      "description": "Agent name or identity of the intended recipient"
    },
    "label": {
      "$ref": "#/$defs/Label",
      "description": "Data label with compartments and policy"
    },
    "policy": {
      "type": "string",
      "enum": ["any", "all"],
      "default": "any",
      "description": "Effective boundary policy for this message"
    },
    "timestamp": {
      "type": "string",
      "format": "date-time",
      "description": "Message creation timestamp (RFC 3339 UTC)"
    },
    "payload": {
      "type": "object",
      "description": "Message body; content is application-specific"
    },
    "trace_id": {
      "type": "string",
      "format": "uuid",
      "description": "Correlation ID linking to boundary check trace"
    }
  },
  "$defs": {
    "Label": {
      "type": "object",
      "properties": {
        "compartments": {
          "type": "array",
          "items": {
            "type": "string",
            "minLength": 1,
            "pattern": "^[ -~]+$"
          },
          "uniqueItems": true
        },
        "policy": {
          "type": "string",
          "enum": ["any", "all"],
          "default": "any"
        }
      },
      "required": ["compartments"],
      "additionalProperties": false
    }
  },
  "required": [
    "protocol",
    "id",
    "origin",
    "destination",
    "label",
    "timestamp",
    "payload"
  ],
  "additionalProperties": false
}
```

### 5.1.2 Field specifications

| Field | Required | Auto-generated | Description |
|-------|----------|---------------|-------------|
| `protocol` | YES | YES | Set by the boundary infrastructure to `dbp/1.0` |
| `id` | YES | YES | UUID v4, generated by the boundary infrastructure |
| `origin` | YES | YES | Set from the sending agent's Agent Card `name` |
| `destination` | YES | NO | Specified by the sending agent or orchestrator |
| `label` | YES | SEMI | If omitted, defaults to unrestricted (`[]`, `any`); cannot exceed clearance (R2) |
| `policy` | NO | NO | Defaults to `any` if omitted |
| `timestamp` | YES | YES | RFC 3339 UTC, set when message is created |
| `payload` | YES | NO | Application-specific body; can be any valid JSON object |
| `trace_id` | NO | YES | Populated after boundary check; linked to trace record |

**Notes:**
- `id` is generated AFTER the boundary check passes and MUST NOT be predictable before the check.
- `origin` MUST match the agent name in the Agent Card. The boundary infrastructure enforces this; the agent cannot forge it.
- `label` MAY be omitted for unrestricted data. If present, it MUST pass the agent's clearance (R2).
- `trace_id` is populated by the boundary infrastructure and MAY be absent in messages that have not yet been checked. A fully processed message MUST have a `trace_id`.

```json
  "label": {
    "compartments": ["fitness", "schedule"],

  },
  "trace_id": "bb8c5a10-1a2b-3c4d-5e6f-7a8b9c0d1e2f"

```

**Unrestricted message:**

```json
{

}
```

## 5.2 Label encoding

### 5.2.1 The label object

The `label` field in a DBPMessage is always an object with two properties:

```json
{
  "compartments": ["engineering", "fitness"],
  "policy": "any"
}
```

**Short form for empty compartments:**

```json
{
  "compartments": [],
  "policy": "any"
}
```

### 5.2.2 Label as a header

When DBP messages are carried over a transport protocol that uses headers (HTTP, for example), the label SHOULD be encoded as a structured header field. Two header fields are used:

| Header | Value | Example |
|--------|-------|---------|
| `X-DBP-Label` | Comma-separated compartments | `X-DBP-Label: engineering, fitness` |
| `X-DBP-Policy` | `any` or `all` | `X-DBP-Policy: any` |

If the label has zero compartments (unrestricted), the `X-DBP-Label` header SHOULD be omitted and the recipient treats the label as empty.

**HTTP example:**

```
POST /message HTTP/1.1
Host: agent-server.local
Content-Type: application/json
X-DBP-Label: fitness, schedule
X-DBP-Policy: any
X-DBP-Origin: coach
X-DBP-Destination: nutritionist
X-DBP-Trace-ID: bb8c5a10-1a2b-3c4d-5e6f-7a8b9c0d1e2f
```

### 5.2.3 Label in file frontmatter

For file-based data transfer (markdown, YAML, JSON files):

```yaml
---
dbp-label: [engineering, fitness]
dbp-policy: any
dbp-origin: coach
dbp-destination: nutritionist
dbp-trace-id: bb8c5a10-1a2b-3c4d-5e6f-7a8b9c0d1e2f
dbp-protocol: dbp/1.0
---
```

### 5.2.4 Label in gRPC metadata

```protobuf
message DBPMetadata {
  repeated string compartments = 1;
  string policy = 2;
  string origin = 3;
  string destination = 4;
  string trace_id = 5;
  string protocol = 6;
}
```

gRPC metadata is attached as a trailing or leading metadata entry.

## 5.3 Transport mappings

| Transport | Label location | Required headers/fields |
|-----------|---------------|-----------------------|
| HTTP | `X-DBP-*` headers | `X-DBP-Label`, `X-DBP-Policy` |
| File (markdown) | YAML frontmatter | `dbp-label: [...]`, `dbp-policy:` |
| File (JSON) | Top-level `label` field | As per JSON schema |
| gRPC | gRPC metadata | `dbp-label`, `dbp-policy` |
| WebSocket | JSON frame top-level | As per JSON schema |
| Local IPC | Serialized JSON | As per JSON schema |
| Environment variable | `DBP_LABEL` | Colon-separated compartments |

A DBP-compliant transport binding MUST preserve the label, policy, origin, destination, and trace_id across the transport. Loss of any of these fields is a protocol violation.

## 5.4 Error handling

### 5.4.1 Malformed messages

If a DBPMessage does not conform to the JSON schema, the receiving boundary infrastructure MUST reject it with an error.

| Error | HTTP status | Description |
|-------|-------------|-------------|
| `MALFORMED_MESSAGE` | 400 | JSON parse failure or schema validation failure |
| `MISSING_FIELD` | 400 | A REQUIRED field is absent |
| `INVALID_PROTOCOL` | 400 | `protocol` field is not `dbp/1.0` |
| `INVALID_LABEL` | 400 | Label does not conform to Label schema |
| `INVALID_TIMESTAMP` | 400 | Timestamp is not valid RFC 3339 |
| `ORIGIN_MISMATCH` | 403 | `origin` does not match the sender's Agent Card |
| `CLEARANCE_EXCEEDED` | 403 | Label contains compartments outside sender's clearance (R2) |
| `BOUNDARY_BLOCK` | 403 | Boundary check failed; data not delivered (R1, R3) |
| `SIZE_EXCEEDED` | 413 | Payload exceeds deployment limit |

### 5.4.2 Error response format

All error responses follow a uniform format:

```json
{
  "error": "BOUNDARY_BLOCK",
  "message": "Label {fitness, schedule} blocked for clearance {identity, project} under policy ANY",
  "trace_id": "bb8c5a10-1a2b-3c4d-5e6f-7a8b9c0d1e2f",
  "timestamp": "2026-07-15T14:30:00.123Z"
}
```

### 5.4.3 Boundary block semantics

When a boundary check returns BLOCK:

1. The message MUST NOT be delivered to the destination agent.
2. A trace record MUST be created with `result: "BLOCK"` (R5).
3. The sender SHOULD receive a `BOUNDARY_BLOCK` error response.
4. The BLOCK SHOULD be logged for audit (via BTL or equivalent).

The BLOCK is **not** a timeout or transient error. It is a deterministic access denial. Retrying the same message with the same label and clearance will always produce the same result.

### 5.4.4 Escalation

If a human or automated supervisor overrides a BLOCK, the override MUST:

1. Create a new agent session with adjusted clearance.
2. The original trace record remains BLOCK — it is never mutated.
3. The escalated message is re-sent through the normal boundary check with the new session's clearance.

This ensures the audit trail always reflects the original denial even when overrides occur.

## 5.5 Processing pipeline

```
Sender creates message m with label L
         │
         ▼
  [R2 check: L ⊆ C_sender?]
         │
         ├── NO  → CLEARANCE_EXCEEDED error
         │
         ▼ YES
  [R3: boundary check: B(L, C_receiver)?]
         │
         ├── BLOCK → BOUNDARY_BLOCK error + trace (R5)
         │
         ▼ PASS
  [Generate id, trace_id, timestamp]
         │
         ▼
  [Encapsulate in DBPMessage]
         │
         ▼
  [Send over transport]
         │
         ▼
  Receiver processes message m
  Heritage applied to any derived data (R4)
```

## 5.6 Schema versioning

The `protocol` field uses the format `dbp/<major>.<minor>`. A change to the REQUIRED fields or their semantics increments the major version. A change that adds OPTIONAL fields or relaxes constraints increments the minor version.

| Version | Changes |
|---------|---------|
| `dbp/1.0` | Initial specification |
